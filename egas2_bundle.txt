##CHARTER.md##
# EGAS SysML v2 Pilot Charter

## Purpose

Rebuild a scoped EGAS system architecture in SysML v2 using SPES viewpoints, then evaluate whether the model improves traceability, consistency, and architecture-level reasoning.

## Background

- The legacy inventory contains 31 files, 13,769 lines, and 1,963 commented lines.
- Eight legacy requirement-related packages participate in an import cycle.
- The legacy logical viewpoint files are almost entirely commented out.
- EGAS v6.0 identifies SZ-01 as unintended acceleration, ASIL B; SZ-02 through SZ-04 are considered controllable and excluded.
- EGAS calls for monitoring across L1 function, L2 functional monitoring, and L3 controller monitoring.
- The L3 concept uses Q&A between the functional controller and an independent monitoring module.
- EGAS gives a Q&A repetition interval of 80 ms or less and at least 10 questions.
- PVS dual-channel faults have specified limp-home responses that provide a grounded safety scenario.
- SPES calls for consistency across actors, goals, scenarios, requirements, and interface inputs and outputs.
- EGAS cites ISO 26262:2011; the pilot uses ISO 26262:2018 terminology while retaining EGAS references as sources.

## Scope

The pilot covers gasoline manifold injection with torque-comparison monitoring and L3 Q&A. Its Golden Paths are GP-A, the SZ-01 L2 monitoring path, and GP-B, PVS dual-channel fault response to limp home (EGAS 11.1.1). Brake override remains a thin scenario.

The pilot uses one architecture level. Gasoline direct injection, diesel torque comparison, diesel acceleration comparison, gasoline acceleration comparison, and A-SaCo are out of scope; the decision rationale is recorded in REGISTRY.md.

The viewpoint order is Objective, Needs, Context, Safety, SHR, Validation, Scenario, System Behavior, System Requirements, Functional BB/WB, Logical BB/WB, and Verification/Views. SHR remains a separate layer and a subtype of hard goal.

## Non-goals

- Reproducing the entire legacy model.
- Producing a certification-ready safety case.
- Modeling detailed hardware/software design, including WCET and per-step millisecond allocation.
- Deeply modeling every use case.
- Developing new modeling tools.

## Modeling and evidence rules

- Top-level model packages use `EgasArch_<Layer>_<Name>` and import only lower layers.
- Define reusable quantities and numeric catalogs in Common; cite source and status for values.
- Use MonitoringLevel for EGAS L1-L3. Use SafeStateStage for safe-state progression.
- UF means black-box user function; FN means white-box function; LC means logical component.
- Do not present assumed safety values as standard or approved values.
- Use the seven-item 1/3/5 scoring rubric and AQ1-AQ8 in EVAL_PLAN.md.

## Budget and completion

Keep the current 2,500-line total budget, layer-specific line/definition budgets, migration curve, and five non-goals in KPI.md and kpi_config.json. The approximate monthly budget is 2,000 AI Credits; 64 Credits per Task is a planning reference, not a quality-reducing hard cap. Carry work into the next month when needed.

Completion requires the selected scope and both Golden Paths to be represented, all hard KPI checks to pass, all eight acceptance questions to be answerable at T21, and no edits to legacy model files. Gate reviews sample model content against the legacy inventory and cited standards; this pilot is not a safety certification.
##COMMON_METADATA_DECISION.md##
# Common Metadata Decision

## Decision

- Use metadata definitions for provenance and classifications that are attached to model elements: `SourceRef`, `ValueStatus`, `GoalData`, `ScenarioData`, and `AbstractionLayer`.
- Keep `ValueStatusKind` as the enum for `Standard`, `project`, `pilotAssumed`, `tbd`, and `reviewed`. The distinct names avoid a global namespace collision between an enum and a metadata definition. KPI counting normalizes `Standard` to `standard`.
- Keep quantitative constraints as typed attributes in Common catalogs, with `SourceRef` and `ValueStatus` applied to each value.
- Represent failure rates with the standard frequency quantity and define the project FIT conversion factor in Common: one FIT equals 1e-9 failures per hour. This is a unit conversion, not an allocated safety target.
- Keep cross-element references as identifier strings in this seed. Replace them with typed SysML relationships when the project relationship patterns are validated in T03.

## Rationale

Metadata expresses classification and provenance; attributes hold queryable values and constraints. The legacy `MetaInformation` only covers version, updater, and change note, so it remains a separate configuration-management concern rather than being overloaded for safety provenance. Existing metadata application syntax is known from the legacy model, but every new enum-typed application must pass current SysIDE diagnostics before it is treated as a verified pattern.

# Evaluation Plan

## Scoring rubric

Score each criterion 1, 3, or 5 using the observable evidence below. Record the score and evidence at T24; do not infer safety validity from model completeness.

| Criterion                      | 1 point                                                                      | 3 points                                                                | 5 points                                                                                                   |
| ------------------------------ | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Expressiveness                 | Required architecture concepts cannot be represented without losing meaning. | The scoped concepts are represented, with some manual workarounds.      | The scoped concepts are represented directly with reusable SysML v2 structures and views.                  |
| Traceability                   | Important relationships are missing or only described in prose.              | Main relationships exist, but coverage or navigation is incomplete.     | The required chains are explicit, navigable, and queryable across viewpoints.                              |
| Consistency maintenance        | Contradictions and omissions are not detected.                               | Some checks are automated; remaining checks need manual review.         | Key SPES consistency rules are checked repeatably and violations are actionable.                           |
| Tool maturity                  | Core editing or validation is unreliable or blocked.                         | Text editing and diagnostics work, with known limitations documented.   | Modeling, diagnostics, queries, and supported views work repeatably for the pilot.                         |
| AI collaboration efficiency    | Cards and constraints do not prevent substantial rework.                     | The AI completes bounded work with user corrections and review.         | Card-scoped work is reproducible, traceable, and reviewable with recorded effort.                          |
| Effort vs. document-based work | Modeling adds effort without reusable or traceable results.                  | Effort is comparable, with some reusable structure or automated checks. | Reuse and automation reduce repeated effort while preserving reviewable evidence.                          |
| ISO 26262 suitability          | Safety concepts or values are misrepresented or lack provenance.             | Relevant concepts are mapped with limitations and assumptions stated.   | Applicable concepts use 2018 terminology, EGAS sources are traceable, and unsupported claims are excluded. |

## Acceptance questions

An answer is acceptable when the model produces the requested elements and their relationship evidence. A justified empty result is acceptable for a coverage query; an unexplained missing result is not.

| ID  | Question                                                                 | Evidence required                                                               |
| --- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| AQ1 | Which logical components and functions satisfy a Safety Goal?            | SG-to-requirement-to-function/component trace chain.                            |
| AQ2 | Which SGs and SYSRs are affected when a component changes?               | Impact path from component through allocations and requirements to SGs.         |
| AQ3 | Which functions or components satisfy no SYSR?                           | Complete satisfy/allocation coverage query, including a justified empty result. |

# EGAS2 Modeling Rules (lint L1-L8)

Run `python egas2/tools/lint.py`. ERROR blocks closing a Task; WARNING does not. `registry_enforced` in `kpi_config.json` turns L1 from WARNING to ERROR.

| Code | Checks                                                                                                                 | Fix                                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| L1   | Definition is not in REGISTRY.md                                                                                       | Register the concept first (concept-registry-guard)                                       |
| L2   | Duplicate definition or Registry row; Registry home package differs from the defining package; invalid status          | Merge, or correct the home package. Status is one of planned, active, retired, outOfScope |
| L3   | Defined but `retired` or `outOfScope` (ERROR); defined but still `planned` (WARNING)                                   | Set the Registry status to `active` when the definition lands                             |
| L4   | A package references a higher layer, or packages import each other in a cycle                                          | Move the shared concept down to the lower layer or Common                                 |
| L5   | Relationship used outside its allowed layers                                                                           | See the table below                                                                       |
| L6   | `EgasSystem` or `LogicalEgasSystem` contains `part`, `perform`, `action`, `state`, `exhibit`, or `assert`              | Keep only `port` and `doc` in a black box                                                 |
| L7   | SPES hints: `@GoalData`/`@ScenarioData` placement, scenario pre/postcondition, scenario to goal, hard goal to scenario | See Hint rules below                                                                      |
| L8   | Literal attribute value without both `@SourceRef` and `@ValueStatus`                                                   | Add both annotations directly before the attribute                                        |

## Relationship placement (L5)

| Relationship                     | Allowed layers                      | Direction and meaning                                                                                                                                                    |
| -------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `#refinement` dependency         | Scn, Beh                            | A scenario or behavior refines a goal or SHR. Scenarios and behaviors never `satisfy` requirements; a legacy `satisfy` in a scenario becomes `#refinement` when migrated |
| `#derivation` connection         | Sysr                                | A SYSR derives from another SYSR. The SYSR to SHR trace is not covered by L5 (`#refinement` is only allowed in Scn and Beh); its pattern is open and decided in T12      |
| `satisfy requirement ... by ...` | Fbb and above (`satisfy_min_layer`) | A functional or logical design element satisfies a requirement                                                                                                           |
| `allocate ... to ...`            | Lbb, Lwb                            | A function (FN) is allocated to a logical component (LC)                                                                                                                 |

## Syntax verified with Syside (T04)

| Construct          | Form that gave no diagnostic                                                                         | Needs                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| refinement         | `#refinement dependency name from A to B;`                                                           | `private import ModelingMetadata::*;`                                                             |
| derivation         | `#derivation connection { end #original ::> a; end #derive ::> b; }`                                 | not yet used in the chain                                                                         |
| satisfy            | `satisfy requirement name : ReqDef by designUsage;`                                                  | design usage declared as `action x : Def;` or `part x : Def;`                                     |
| allocate           | `allocation name : Allocation allocate fn to lc;`                                                    | `private import Allocations::*;`                                                                  |
| verify             | `verify reqUsage;` inside `verification def { objective { ... } }`                                   | `VerificationCases`; `reqUsage` must be an existing requirement usage, not a new name with a type |
| viewpoint and view | `viewpoint def V { doc ... }`, `view v : GeneralView { viewpoint p : V; satisfy p; expose Pkg::*; }` | `StandardViewDefinitions`                                                                         |

- Give every usage a name that is unique across layers. Two usages named `l2Monitor` in Fbb and Lwb would make `satisfy` and `allocate` ambiguous.
- A package that only needs an enum or metadata from Common imports it; `ModelingMetadata` is not pulled in by Common.

## SPES hint rules (L7)

- Write `@GoalData { ... }` and `@ScenarioData { ... }` directly before the element they describe, like `@SourceRef`. The lint reads the next element name as the owner.
- A scenario gives `fulfills = ("G1", ...)`, `preCondition`, and `postCondition` (Hints 4-2, 4-3). Every fulfilled id must be a described goal.
- Every goal with `kind = GoalKind::hard` must be fulfilled by at least one scenario.
- Not yet checked mechanically: context-actor to scenario-actor match (Hint 4-1) and input/output consistency (Hints 4-4 to 4-7). They need Ctx and Scn models and are added in T06 and T10.

## Limits

The scanner is regex based. It handles declarations written on one line or many, but not macros or generated text. Fixtures in `egas2/tools/test_lint.py` document the accepted forms.
